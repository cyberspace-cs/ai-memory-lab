# AI Agent 记忆系统的六维设计空间

> 初稿 v1（2026-09-20）。写作素材全部来自 ai-memory-lab 仓库的源码走读与实测，代码均可复现。
> 数据：mem0 65.7k / LightRAG 39.8k / graphiti 31.0k / cognee 30.8k star（2026-09 实查）。

## 一、为什么 Agent 需要记忆工程，而不是"存聊天记录"

一个真实场景：你告诉 Agent"我住在上海"，三天后它给你推荐上海的咖啡店——这没问题。两周后你说"我搬到了北京"，它应该记住新事实，但你问它"我该把上海的公积金怎么转"，它最好还记得你曾经住过上海。

现在把这三句话换成语料喂给市面上任何一个"带记忆"的 Agent 框架，然后问两个问题：**它现在的"事实"是什么？它凭什么这么认为？** 你会发现大多数实现只能回答第一个，第二个的答案通常是"因为向量库里检索到了这条 chunk"——这不是记忆，这是缓存。

我们 yardstick 化了四个高星项目（mem0、graphiti、cognee、LightRAG）加上 letta 的源码，把"记忆系统"拆成六个可以独立评价的维度：

| 维度 | 一句话定义 | 典型事故 |
|---|---|---|
| ① 信息提取 | 从对话/文档中把"值得记的"捞出来 | 闲聊被存成事实，事实被漏掉 |
| ② 知识结构化 | 记什么类型、什么粒度 | 全存自由文本，检索全靠运气 |
| ③ 实体关系建模 | 实体归一、关系成图 | "字节/ByteDance/字节跳动"是三个实体 |
| ④ 冲突消解 | 新旧矛盾谁说了算 | 新旧并存，检索到哪条算哪条 |
| ⑤ 来源追溯 | 每条知识说得出出处 | 无法审计，无法纠错 |
| ⑥ 动态更新 | 增量写入、衰减、演化 | 全量重建一次 20 分钟 |

下面逐维拆解设计空间，最后给出我们的答案 MemEngine——以及三个只有动手实现才会踩到的坑。

## 二、六维逐个拆

### ① 信息提取：mem0 用三次架构演化告诉你的事

mem0 的经典两阶段是教科书：先 LLM 抽取候选事实，再让 LLM 拿候选与旧记忆对比，裁决 ADD/UPDATE/DELETE。但我们克隆最新主干的 `main.py`（3868 行）时发现，`add()` 的主路径已经换成了 **V3 additive 管线**：一次 LLM 调用只做抽取（只产 ADD），UPDATE/DELETE 从主路径消失了，取而代之的是 MD5 哈希去重、`linked_memory_ids` 显式链接、实体批量合并。

这是三家厂商里最值得玩味的信号：**"每条候选都拉一次 LLM 做裁决"在工程上不可持续**。mem0 用确定性的哈希和链接规则吃掉了大部分冲突场景，把 LLM 挪出了热路径。另一个细节是对话里的时间表达必须锚定到 Observation Date（对话发生的时刻）而不是系统当前日期——"上周去巴黎"半年后检索时必须还是绝对的日期。

### ② 知识结构化：letta 的分层与 cognee 的模式

letta（MemGPT）的贡献是分层：core memory（agent 可以自己编辑的块）、archival（向量库）、recall（消息史），agent 通过工具调用在层间搬运信息。cognee 的贡献是**抽取目标是一个 pydantic 模型**：`graph_model` 参数决定图长什么样，LLM 按模型做结构化输出，还能挂本体文件。类型声明替代了自由发挥，这让"记忆里有什么类型的东西"变成了可审计的 schema，而不是 prompt 里的玄学。

### ③ 实体关系建模：图不是目的，归一才是

GraphRAG/LightRAG 都会抽实体关系建图，但工程上的胜负手不在建图，在**归一**：mem0 主干里实体合并是"精确匹配 or 语义相似度≥0.95"，cognee 干脆用确定性 id（`Entity:<name>`）让重新提及的实体自动归位。graphiti 更彻底：episodic 节点（原文块）和 entity 节点分存，关系边必须挂在实体之间——图因此有了骨架而不是一团向量。

### ④ 冲突消解：两派之争与一条被忽略的公理

这里是我们花时间最多的维度，两条路线：

- **LLM 裁决派**（mem0 经典版）：候选事实和旧记忆一起塞给 LLM，输出 ADD/UPDATE/DELETE。简单、语义理解强，但每次裁决都是黑箱，且贵。
- **双时态失效派**（graphiti）：不做"谁对谁错"的判断，只做时间标记——旧边 `invalid_at = 新边.valid_at`（业务轴），同时 `expired_at = now`（事务轴）。矛盾判定本身仍由 LLM 做（小模型 + 结构化输出），但**失效的执行是纯机械的**。

而 cognee（issue #3631）补上了被大多数实现忽略的公理：**哪些关系是单值的（函数型的），不能靠推断，只能声明**。"现任 CEO"是单值的，"认识的人"是多值的；前者才允许新值顶旧值，后者新旧并存。LLM 抽出来的关系没有基数元数据，你没法偷懒。

我们的取舍见第四节。

### ⑤ 来源追溯：一条不变量就够

graphiti 的 episodic 节点是最优雅的设计：每条关系边必须由某个 episode（原文块）产生，来源不是元数据字段，而是**图上的强制连接**。我们把它简化成一条入库不变量：`source is None` 的事实拒绝入库。有了它，"你凭什么这么认为"永远有答案。

### ⑥ 动态更新：增量 vs 批处理是分水岭

GraphRAG 的图是全量重建的，改一条文档跑一次社区检测——适合静态语料问答，不适合 Agent。graphiti/LightRAG/cognee 都把增量当作默认。剩下的是细节：衰减（低置信归档）、演化（新记忆触发旧记忆改写，A-mem 的 Zettelkasten 式思路）、以及**重复的另一个用法**——graphiti 遇到重复边不是丢弃，而是把新 episode 追加到旧边上，"这条事实被多少个来源印证过"成为可查信号。

## 三、实测：三条时间线让框架现原形

我们写了两个验收语料（都在仓库里可复现）：

**语料 A（个人记忆）**：20 轮对话，含三处反转——换城市（上海→北京）、换手机（iPhone 15→小米 15）、改偏好。外加两个陷阱：一条**重复陈述**，一条**迟到重提**（六月在七月之后重新说"我住上海"）。

**语料 B（运维事件单）**：09:00 P0 告警 → 09:15 初判"pay-service 超时引发雪崩" → 09:40 更正"根因是连接池耗尽，pay-service 超时是结果"。这条语料的价值在最后一问：**初判还是真相吗？**

对 nano-memory 之外我们没有跑全量对比（成本原因），但走读可以给出预期行为：LLM 裁决派会正确处理但丢失过程；双时态派正确且可回溯。我们自己的 MemEngine 输出如下裁决日志：

```
ADD        no conflicting (subject,predicate)
SUPERSEDE  same key ('用户','lives_in'), object '上海' -> '北京', t 01-10 <= 06-01
DEFER_LLM  resurrection: '上海' was superseded by item 60bf45...; stale recall vs correction needs review
```

三条日志对应三种裁决路径，每条带证据。特别注意第三条——这是实测逼出来的规则：**迟到重提一个已被顶掉的旧值，必须挂起待复核**，因为"迟到的复述"和"真实的更正"在规则层不可区分。没有这条规则，六月的那句"我住上海"会靠时间戳把北京翻盘。

另一个顺手的收获：每次 SUPERSEDE 天然构成一个（错误认知 → 正确保留）的**更正对**，导出即可进 RFT 训练管线。记忆系统顺手成了训练数据工厂——这是我们做这个项目前没预料到的。

## 四、我们的答案：MemEngine 与三个坑

MemEngine（nano-memory，约 900 行纯标准库）的定位是**审计优先的增量记忆引擎**，四条不变量：

1. 没有来源的事实拒绝入库
2. 被更正的事实永不物理删除（"当时的真相"可查）
3. 同一（主体，函数型谓词）任一时刻最多一条 current
4. 每次裁决必留证据链

冲突消解是四档规则优先、LLM 兜底：NOOP（重复→印证累积）→ SUPERSEDE（时间可判）→ 并存（限定条件不同/多值关系）→ DEFER_LLM（不可判，挂起待人工）。LLM 挂掉时系统降级运行而不是报错。

三个坑，都属于"读源码看不出来，写测试立刻炸"：

1. **事务时间 ≠ 业务时间**。第一版把 episode 的时间戳回填成事实的生效时间，结果"时间未知"被掩盖，本该挂起的冲突被错误裁决。graphiti 的 `expired_at` 与 `valid_at` 分离不是洁癖，是刚需。
2. **同键双 current**。规则没写全的时候，同一个（主体，谓词）会出现两条并存的事实——图看着没问题，检索时随机命中。我们最终用不变量 3 + 测试断言锁死。
3. **旧值复活**。前文说过的迟到复述翻盘问题。

项目本身在 github.com/cyberspace-cs/ai-memory-lab，fork 了 mem0/graphiti/cognee/LightRAG/letta 五个仓库，走读笔记和 24 个测试全部公开。

## 五、开放问题

- **规则覆盖率的天花板在哪？** 我们的四档规则能处理状态型事实（地址/设备/根因），但"喜欢甜咖啡"vs"喜欢冰美式"这类纠缠仍需 LLM。DEFER 队列积压了怎么办？
- **多租户与记忆共享的边界**：graphiti 用 group_id 硬隔离，团队记忆和个人记忆的交叉授权怎么做？
- **衰减由时间驱动还是访问驱动？** 半衰期模型简单，但"用户三个月没提的偏好"未必不重要。

评论区聊聊你的 Agent 是怎么做记忆的。
